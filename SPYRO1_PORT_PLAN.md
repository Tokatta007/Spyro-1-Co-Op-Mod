# Spyro 1 co-op port — build system plan

Working design for stage 3. Companion to `CLAUDE.md`; that file holds the
verified facts, this one holds the plan and the reasoning.

Status: **skeleton built, byte-identical rebuild gate PASSES** (2026-08-05).
Free BIOS RAM confirmed on hardware-accurate emulation. Next: first hook.
See "Order of work" below.


## What we are copying

Spyro2x2's architecture, not C0mposer's. Recap of why:

| | Spyro2x2 | C0mposer's `mods/` |
| --- | --- | --- |
| Code lives in | PS1 BIOS scratch RAM | extra 8 MB dev RAM |
| Hook method | rebuild EXE, replace instructions | overwrite 1st instruction with jump |
| Runs on a real PS1 | **yes** | no (needs 8 MB) |
| Good for | shipping | quick RE testing |

C0mposer's repo is a **symbol source**. Do not copy its build approach.


## Verified facts (see CLAUDE.md for hashes)

Spyro 1 `SCUS_942.28`, 417,792 bytes = `0x800` header + `0x65800` body.

PS-EXE header fields:

```
0x10  PC      = 0x8005b8e0     entry point
0x18  t_addr  = 0x80010000     load address
0x1C  t_size  = 0x00065800     body size
```

Resulting memory map:

```
0x80000000 .. 0x8000FFFF   PS1 BIOS kernel area   <- mod code goes here
0x80010000 .. 0x80075800   game .rodata/.text/.data (loaded from file)
0x80075800 ..              game .bss (not in file)
0x801FFFFF                 end of 2 MB RAM
```

Lowest known Spyro 1 symbol is `0x80010a70`. The game touches **nothing**
below `0x80010000`, exactly like Spyro 2.


## Disc layout (from dumpsxiso)

Much simpler than Spyro 2's 197 WADs:

```
SYSTEM.CNF          license_data.dat
SCUS_942.28         <- the executable we patch
WAD.WAD             <- contains 36 level overlays
```

### Per-file notes

**`symbols.ld` — write this first.** It is just `name = 0xADDRESS;` lines.
Seed it from the CLAUDE.md symbol map, then grow it from
`decomps/open-spyro/config/symbol_addrs.txt` (613 named functions) as needed.

> **TRAP:** in Spyro2x2, the addresses in the *comments* in `Sp2.h` are the
> **PAL** build. Each project's `symbols.ld` overrides them (NTSC `sp2_ticks`
> is `0x80067018`, PAL is `0x8006c580`). Do not treat header comments as
> authoritative. For Spyro 1 we target NTSC only, so keep ONE address set and
> put it in `symbols.ld`.

**`main.S` — the hook list.** Same pattern as Spyro2x2:

```asm
.incbin "rom/SCUS_942.28", 0x800, <len>   # original bytes
/* 0x800xxxxx */ jal Sp1x2Graphics         # one replaced instruction
.incbin "rom/SCUS_942.28", <off>, <len>   # resume
```

Each hook needs: the file offset, the instruction's RAM address, and the
correct chunk lengths either side. File offset = `RAM addr - 0x80010000 +
0x800`. Getting a length wrong shifts everything after it and corrupts the
executable, so add hooks **one at a time** and test.

**`Makefile`.** Spyro 1 has no 197-WAD repack, so `rewad.py`/`unwad.py` are
not needed initially. `DISCLIST` becomes the file list above. `make setup`
still runs `dumpsxiso`.


## Delivery: getting mod code into the BIOS region

Spyro2x2 used three regions:

| Region   | Origin       | Length   | How the bytes get there |
| -------- | ------------ | -------- | ----------------------- |
| `LOADER` | `0x8000B070` | `0x800`  | PS-EXE header padding   |
| `BIOS2`  | `0x8000C000` | `0x1F00` | WAD slot 72             |
| `BIOS3`  | `0x8000E400` | `0x1C00` | WAD slot 74             |

**`LOADER` transfers to Spyro 1 — CONFIRMED 2026-08-04.** Booted Spyro 1 in
PCSX-Redux (real SCPH1001 BIOS, dynarec off) and read memory at
`0x8000B070`: the ASCII string **`PS-X EXE`** is present. That is the magic
number at the start of a PS-EXE header, which proves `0x8000B070` is the BIOS
kernel's header-read buffer — the BIOS loads the whole 2 KB header there and
never clears it. `LENGTH = 0x800` in Spyro2x2's linker script matches the
header size exactly, confirming this is the same trick.

Only the first `0x80` bytes are real header fields, so
**`0x8000B0F0` .. `0x8000B870` = 1,920 bytes of free RAM**, available with no
cooperation from the game. This is BIOS behaviour, not game behaviour.

**`0x8000B870` holds the BIOS EXEC structure — do not touch.** Read at the
title screen: `E0 B8 05 80` = little-endian `0x8005b8e0`, which is Spyro 1's
entry point from the PS-EXE header. That is the BIOS's exec parameter block
(pc0 first). This is why `LOADER`'s `LENGTH = 0x800` stops dead at
`0x8000B870` — Spyromain ended one byte short of live BIOS data. Treat
`0x8000B870` as a hard ceiling.

**`BIOS2` and `BIOS3` also appear free — CONFIRMED IN-LEVEL 2026-08-04.**
Checked while walking around Artisans Home (not just the title screen):

| Address      | Title screen | In-level | Verdict |
| ------------ | ------------ | -------- | ------- |
| `0x8000B0F0` | header padding ("Sony Computer Entertainment Inc. for North America area") | unchanged | free — BIOS reads it at load time only |
| `0x8000C000` | zeros        | zeros    | free    |
| `0x8000DF00` | zeros        | zeros    | free (his gap here looks like margin, not avoidance) |
| `0x8000E400` | zeros        | zeros    | free    |
| `0x8000B870` | **EXEC struct** | —     | **IN USE — hard ceiling** |

So Spyromain's full memory map ports to Spyro 1 essentially unchanged: about
**18 KB** across `LOADER` + `BIOS2` + `BIOS3`.

**Residual risk, partially retired 2026-08-06.** The first hook writes markers
to `0x8000C000`/`0x8000C004` every frame, and those survived **FMV playback**
and **CD loading** intact — so video and level streaming do not trample at
least the start of `BIOS2`. Still untested: the `S0/CRASH.EXE` demo,
memory-card save/load, and levels other than the early ones. If a mystery
crash appears after adding code here, re-check these addresses during whatever
the game was doing at the time.

**The RAM is free, but DELIVERY still differs.** Confirming `BIOS2`/`BIOS3` are
unused is only half the problem — we still need a way to get bytes *into* them.
Spyromain used WAD slots 72/74, which are Spyro 2 specific and mean nothing
here.

- `LOADER` (`0x8000B0F0`..`0x8000B870`, 1,920 bytes) is **free of this
  problem** — the BIOS copies the header there for us, so simply placing code
  in the EXE header's padding is enough. No game cooperation required.
- `BIOS2` + `BIOS3` (~16 KB) need a delivery path. Options, in preference
  order:
  1. **A copy stub in `LOADER`.** Put a small routine in the header padding
     that memcpy's a larger blob into `0x8000C000`/`0x8000E400` at startup.
     The blob itself still has to live somewhere — likely appended to the EXE.
  2. **Extend `t_size`** and append the blob after the game body. It loads at
     `0x80075800`, which collides with `.bss`, so the stub must copy it out
     before `.bss` is used. Ordering is delicate.
  3. **Hijack a level overlay slot** in `WAD.WAD` — closest to Spyromain's
     approach, but needs Spyro 1's overlay loader understood first.

**Milestone 1 needs none of this.** 1,920 bytes in `LOADER` is enough for the
swap routine and a minimal two-camera render. Prove the pipeline there first;
only solve delivery when we actually run out of room.


## State duplication: Spyro 1 is shaped differently (2026-08-06)

**Spyro 1 has no monolithic state structs.** This is the biggest structural
difference from Spyro 2 and it changes how the swap works.

| | Spyro 2 | Spyro 1 |
| --- | --- | --- |
| Spyro state | `sp2_spyro[708]` — one struct | ~94 separate named globals |
| Camera state | `sp2_camera[500]` — one struct | ~54 separate named globals |
| Swapping it | one `Sp2x2Swap` call | a list of ranges + singles |

C0mposer's `_spyro = 0x80078A58` is **not** a struct — open-spyro names that
exact address `g_anSpyroWorldPos`, `size:0xc`. It is just the XYZ position.
Do not treat it as a Spyro 2-style struct base.

### Only `.bss` needs swapping

`.bss` starts at `0x80075800`. Below that is initialised constant data
(animation tables, camera spring gains) which is identical for both players
and must NOT be swapped. Filtering on that boundary shrinks the job a lot:

| | constants (no swap) | runtime state (must swap) |
| --- | --- | --- |
| Camera | 27 globals, 905 B | **54 globals, 306 B** |
| Spyro  | 23 globals, 2,868 B | **94 globals, 662 B** |

So roughly **1 KB of real per-player state**, not the 3.5 KB a naive count
suggests. That fits comfortably in the free BIOS RAM.

### The core camera block is contiguous

Most camera state is one tight cluster:

```
0x80076dd0  g_anWorldToCameraRotMtx   (+20)
0x80076df8  g_anCameraPos             (+12)
0x80076e04  g_anCameraEyeTarget       (+12)
...
0x80076ed0  g_anCameraScriptedTargetPos (+12)
```

~`0x110` bytes covering the matrix, position, target, euler angles, spring
state and mode. A single range swap could handle nearly all of it, plus a
handful of strays (`0x800758xx` shake/timers, `0x8007704c` gem-pickup path,
`0x80078c74` pointers).

> **VERIFY BEFORE RANGE-SWAPPING.** The listing above was filtered to symbols
> whose *names* contain "camera". Non-camera globals could sit in the gaps and
> a range swap would corrupt them. An unfiltered dump of
> `0x80076dd0`..`0x80076ee0` showed camera-only up to `0x80076e40`; the rest is
> unchecked. Confirm the whole range before treating it as one block.

### Implication for milestone 1

Two cameras rendering one level needs **only the core camera block** — not all
54 camera globals, and no Spyro state at all. Both players can share Spyro's
position for the first test: same scene, two viewpoints. Even simpler as a
first step, render twice with the *same* camera to prove the double-render
works, then vary it.


## GamestateDraw, decompiled (2026-08-06)

**`decomps/open-spyro/src/c/GamestateDraw.c` is the single most useful file in
any of the three decomps.** 166 lines of readable C for the exact function we
hook. Read it before writing any render code.

(open-spyro is the most advanced of the three: 11.75% matched, 613 named
functions, verified byte-identical. `spyro-1` uses raw `func_8001ED5C` names
but groups files by topic — useful as a cross-reference. C0mposer's is best
for hand-named globals.)

### Frame environment layout

Same design as Spyro 2, which is why the symbol addresses line up:

| Offset | Contents |
| ------ | -------- |
| `+0x00` | DRAWENV (`0x5c` bytes) |
| `+0x5c` | DISPENV — submitted via `PutDispEnv(env + 0x5c)` |
| `+0x70` | primitive-buffer write cursor |
| `+0x74` | OT depth-bin array base |
| `+0x78` | active depth slot |

The two envs are **`0x84` apart** (`0x80076ee0` and `0x80076f64`) and
GamestateDraw flips between them each frame:

```c
env = &g_abFrameDrawEnv0;
if (g_pActiveFrameDrawEnv == env) env += 0x84;
```

Spyro 2's `sp2_last_primitive = *(void **)&env[112]` is the same `+0x70`
cursor. Same engine lineage — Spyromain's structure transfers.

### Three constraints for two-viewport rendering

1. **`BuildCameraViewMatrix()` is the hinge.** Called once per frame near the
   top of GamestateDraw, before the gamestate dispatch. It turns the camera
   globals into the view matrix. Swap camera state -> call it again -> the next
   pass renders from the other viewpoint. Counterpart of Spyro 2's
   `Sp2AnglesToMatrix`.
2. **Do NOT call `GamestateDraw` twice.** Its gameplay path ends with the full
   frame submit (`DrawSync`, VSync pacing, `PutDispEnv`, `PutDrawEnv`,
   `DrawOTag`). Twice = two frame submits. This is exactly why `Sp2x2Graphics`
   reimplements the body instead of calling the original twice. Our
   `Sp1x2Graphics` will have to do the same for gamestate 0, while passing
   every other gamestate straight through.
3. **Scene building is granular.** Spyro 2 has one `Sp2GraphicsGame()`; Spyro 1
   splits it into `BuildRenderEntityLists`, `ComposeFrameScene`,
   `SetupFrameOT`, `DrawActors`, `RasterizeEmitList`. All are named in
   open-spyro's `symbol_addrs.txt`, so addresses are available — but each must
   be checked for whether it depends on camera state.

### Gamestate values

`g_nGamestate == 0` is gameplay. 1-0xF are menus, cutscenes, save/load,
titlescreen, credits. Our early-out guard is `if (g_nGamestate != 0)
{ GamestateDraw(); return; }` — matching Spyro2x2's demo-mode/pad guard.


## Screen geometry — measured, not guessed (2026-08-06)

Dumped live from the DRAWENV/DISPENV via marker RAM and read in PCSX-Redux:

| | x | y | w | h |
| --- | --- | --- | --- | --- |
| DISPENV (displayed) | 0 | **0 or 240** | **512** | **240** |
| DRAWENV (drawn into) | 0 | **8 or 248** | **512** | **224** |

- **Spyro 1 is 512x240**, with a 512x224 draw area.
- The y values alternate because of the double buffer: buffer 0 displays at
  VRAM y=0 / draws at y=8; buffer 1 displays at y=240 / draws at y=248.
- `draw y = display y + 8` always — an 8-pixel overscan margin top and bottom
  (8 + 224 + 8 = 240).
- VRAM is 1024x512, so the two buffers occupy y=0..480. Comfortable.

### What this means for two viewports

Half of the 224-line draw area is **112 lines each**:

| | draw y | draw h |
| --- | --- | --- |
| Player 1 | `disp_y + 8` | 112 |
| Player 2 | `disp_y + 8 + 112` | 112 |

Compare Spyro 2, where Spyromain used `HEIGHT = 0xd8` (216) with a 12-line
margin. Same structure, slightly different numbers.

**`DRAWENV.ofs` measured (B2):** `ofs.x = 0`, `ofs.y = 0 or 240` — i.e.
`ofs.y == clip.y - 8 == display y`. Geometry is projected into a 0..240 space,
`ofs` puts it at the top of the buffer, and the 8-line overscan comes from
*clipping*, not offsetting. Shifting **both** `clip.y` and `ofs.y` by +112 is
therefore the correct way to place player 2 — confirmed working.

### B1 result (viewport control CONFIRMED)

Shrinking `DRAWENV.clip.h` to half confined rendering to the top half, with
the bottom retaining whatever was there before (loading screen, last frame of
a cutscene). Drawing control works. Spyro appeared low in the top half rather
than centred — correct for a *cropped* view: he sits at the vertical middle of
a 224-line render, which is the bottom edge of a 112-line clip. Squashing
(rather than cropping) is a later refinement — see Spyro2x2's
`Sp2x2ReducePrimitives`, which halves every primitive's Y coordinate.


## Split-screen: two knobs, and which one to use (2026-08-06)

Getting each player's view to sit correctly in its 112-line strip took three
separate mechanisms. They are easy to confuse, so:

| Mechanism | Moves | Use it for |
| --------- | ----- | ---------- |
| `g_anWorldToCameraRotMtx` row 1 | 3D vertex Y **scale** | squashing a 224-line view into 112 |
| `SetGeomOffset(x, y)` | 3D projection **centre** | centring each player's 3D view in its strip |
| `DRAWENV.ofs` | **everything** in the buffer, 3D and 2D | positioning the strip itself |

**Both centring mechanisms were tried. Each breaks something different.**

| Approach | Result |
| -------- | ------ |
| `DRAWENV.ofs.y -= half/2` | 3D fully correct (world AND actors agree). **HUD clipped away** — the gem counter at screen y~20 lands at y=-36, outside the strip. |
| `SetGeomOffset(256, 64)` | **HUD correct.** But every ACTOR (gnorcs, sheep, gems, dragon statues) floats into the sky while terrain stays put. |

**Why `SetGeomOffset` breaks actors.** `RasterizeEmitList` (the world
rasteriser, `0x800573c8`) is flagged **handwritten** in open-spyro's progress
table — Insomniac's hot GTE loops drive the coprocessor directly. So the
terrain path and the actor path do not share a notion of screen centre, and
moving `OFY` moves only one of them. The error scales with distance from
centre, which is why looking at the ground hid it and looking at the horizon
exposed it.

**Current choice: `ofs.y`.** Correct 3D with a clipped HUD beats a correct HUD
with floating scenery. `ofs.y` is applied by the GPU to every primitive
uniformly, so no code path can disagree with it.

**This is deferred, not abandoned.** A single full-size HUD stretched across a
split screen is wrong regardless — it needs per-player handling anyway. Fixing
it properly means reading `DrawActors` (`0x80050bd0`, 5148 bytes) and
`RasterizeEmitList` (3372 bytes, handwritten) to find how each derives screen
Y. Do that as its own task, not as a patch.

**Values, read from the disassembly, not guessed.** Spyro 1 calls
`SetGeomOffset(256, 120)` and `SetGeomScreen(341)` exactly once, at ram
`0x80012814`-`0x80012824`, and never again — so anything we change we must
restore. Per-viewport we use `OFY = (clip_y - ofs_y) + half/2` = `8 + 56` =
**64**, the middle of each strip; the same value works for both players
because each strip is measured from its own `ofs.y`.

**How the centring requirement was diagnosed:** in a screenshot, Spyro was cut
in half exactly on the boundary between the two viewports. He sits at the
projection centre (y=120); squashing compresses content toward that centre, to
64..176; player 1's strip showed 8..120 — so the centre landed precisely on the
clip edge. That one visual detail pinned the required shift at `half/2` = 56.


## Player-2 input: Spyromain's trick, and Spyro 1's equivalents

**He never wrote controller-reading code.** `Sp2x2VSyncCallback` swaps the two
port buffers and calls the game's OWN pad handler a second time:

```c
Sp2x2Swap(&sp2_pad_port_1, &sp2_pad_port_2, sizeof sp2_pad_port_1);
Sp2VSyncCallback();          /* game reads player 2's pad thinking it is P1's */
```

`Sp2x2LogicController` does the same around `Sp2LogicController(0)` /
`Sp2LogicController(1)`. It is the same borrow-run-restore pattern as the
renderer, applied to input. **This is a design, and designs port.**

### Candidate Spyro 1 symbols

| Purpose | Spyro 1 candidate | Address |
| ------- | ----------------- | ------- |
| poll + distribute pad input | `PollPadAndDistributeInput` (0x67c) | `0x80053c68` |
| snapshot pad state | `SnapshotPadInputState` | `0x80053708` |
| pad -> Spyro movement | `ComputeSpyroMoveTargetFromPad` | `0x8003d3b8` |
| pad -> Spyro facing | `ApplyPadInputToSpyroBodyYaw` | `0x8003d840` |
| pad state dispatch | `DispatchSpyroPadStateChanges` | `0x80040f68` |
| buttons held / pressed | `_currentButtonsHeld` / `_currentButtonsPressed` | `0x80077380` / `0x80077378` |
| analog sticks | `_leftAnalogStick` / `_rightAnalogStick` | `0x800773D2` / `0x800773D0` |
| **second controller buffer** | `_secondController` | `0x80078E50` |

`_secondController` already existing is the promising part — Spyro 1 reads
port 2 for something. Find what fills it and whether
`PollPadAndDistributeInput` can be re-run against it with the buffers swapped.

### ANSWERED 2026-08-06: yes, and it is a small job

`_secondController` has exactly ONE reference in the whole executable — an
`addiu` at `0x800123d8` computing its address as an argument inside
`InitPadSystem` (`0x800123c8`). Disassembling that function:

```asm
a0 = 0x800786A0     ; controller port 1 buffer
a1 = 0x80078E50     ; controller port 2 buffer  (= _secondController)
jal 0x8006b010      ; PadInitDirect-style init, BOTH buffers
...
jal 0x80053c68      ; PollPadAndDistributeInput, once at init
a0 = 0x80053c68
jal 0x8005de58      ; InstallVSyncCallback(PollPadAndDistributeInput)
```

| Fact | Value |
| ---- | ----- |
| Port 1 pad buffer | `0x800786A0` |
| Port 2 pad buffer | `0x80078E50` |
| Per-frame pad handler | `PollPadAndDistributeInput` `0x80053c68` |
| Installed as VSync callback at | `0x80012444` (`jal InstallVSyncCallback`) |
| `InstallVSyncCallback` | `0x8005de58` |

**Spyro 1 already polls both controllers every frame** — it hands the BIOS two
buffers at init and simply never uses the second. So Spyromain's trick maps
directly: swap `0x800786A0` <-> `0x80078E50`, run `PollPadAndDistributeInput`
again, swap back.

**Hook plan:** replace the single `jal InstallVSyncCallback` at `0x80012444`
with a jal to our own installer, which registers our callback instead. One
instruction, same pattern as the render hook. Bump `EXPECTED_HOOKS` to 2.


## Beyond Spyro2x2: widescreen, split orientation, 3-4 players

Assessed 2026-08-07, based on mechanisms already built and working.

### Widescreen — EASY. We already have the lever.

`BuildCameraViewMatrix` scales row 1 of the view matrix by `0x140>>9` =
`320/512` = 0.625 — the game's own 4:3 aspect correction (see the squash
notes). Widescreen is the SAME knob with a different number: for 16:9 on a
4:3 render, scale Y by a further 0.75. Our `Sp1x2SquashViewY()` is already
exactly this operation with a factor of 0.5.

So anamorphic widescreen is roughly **one constant**. The display stretches it.

Caveats:
- 2D sprites and the HUD do NOT stretch with it (screen-space, never touch the
  view matrix) — they will look horizontally squashed. Same class of problem as
  the HUD/actor projection question already open.
- Wider FOV can expose geometry the game culls for a 4:3 frustum — expect
  popping at the screen edges.

### Split orientation — EASY, and symmetric to what exists.

Current split is top/bottom: halve `clip.h`, shift `clip.y`/`ofs.y`, and squash
matrix **row 1** (Y).

Side-by-side is the mirror image: halve `clip.w`, shift `clip.x`/`ofs.x`, and
squash matrix **row 0** (X). Every mechanism is already written and proven; only
the axis changes.

Which is better depends on the display. On 16:9: stacked gives each player a
very letterboxed 16:4.5 sliver; side-by-side gives each a narrow 8:9. Modern
games generally prefer side-by-side on widescreen. Worth trying both — it is a
small change now.

### 3-4 players — POSSIBLE, but performance is the wall.

| Piece | Difficulty | Notes |
| ----- | ---------- | ----- |
| Rendering quadrants | MODERATE | Squash BOTH matrix rows (X and Y), clip to a quadrant. Extends naturally from what exists. |
| Per-player state | MODERATE | 3 shadow copies instead of 1, ~1 KB each. Space is adequate (8.3 KB free + BIOS3's 7 KB). |
| **Input (multitap)** | **HARD** | PS1 has 2 ports. `InitPadSystem` (`0x800123c8`) does a PadInitDirect-style init with exactly 2 buffers. Multitap is a different protocol with different buffer layout — we would have to replace that init outright. New low-level code, not an adaptation. Emulators do support multitap. |
| **Performance** | **THE WALL** | We render twice with a `DrawSync` stall and already need 300% overclock. Four renders doubles that again. Removing the stall is necessary but probably not sufficient. |

**Test performance BEFORE writing the multitap driver.** Render 4 viewports with
players 3 and 4 static (no input at all). That exercises the full 4x render cost
in an afternoon and answers the only question that can kill the feature. Same
advice as was given for 4-player Spyro 2 — it applies more now, not less.

### What else would make this a finished mod

Beyond rendering and input, these are the questions that separate "two Spyros
appear" from "a mod people actually play". Most are DESIGN decisions as much as
technical ones — worth deciding deliberately rather than discovering.

**Co-op behaviour (the important ones):**
- **Players getting far apart.** What happens to collision, the camera, and any
  level streaming when player 2 wanders off? Spyromain shipped
  `Sp2x2TeleportSpyro` — almost certainly a "warp to the other player" escape
  hatch. Expect to need one.

### Selecting player count

Save-file slots are a poor fit — they are game data, and hijacking them would
confuse actual saves.

Better: **read a button combo at boot.** `Sp1x2Boot` already runs before the
game starts and the BIOS has already polled both pads by then, so it can read
the port buffers directly (exactly as `Sp1x2UpdatePlayer2Input` does) and store
a mode byte in BIOS RAM. Hold nothing = 2P, hold X = 3P, hold O = 4P. Cheap,
uses infrastructure that exists, no interference with saves.

**A boot menu is nicer, but is a genuinely bigger job — do it second.**
Preferred end state: boot to a menu, pick 2/3/4 players, reset to change.
The honest cost difference:

| | Effort | Why |
| --- | --- | --- |
| Button combo at boot | ~an hour | Read the pad buffer, store a mode byte. All the pieces exist. |
| Proper menu | a day or more | Needs text rendering, menu logic and input handling. At boot-stub time the GPU is not initialised, so we cannot simply draw — it would mean hooking Spyro 1's own title screen (gamestate 0xD, `func_8007CEE4`) and adding an entry to its existing menu, in an unfamiliar UI system. |

Recommendation: build the button combo FIRST so multi-player is testable at
all, then replace it with a title-screen menu as polish. The mode byte and
everything downstream stays identical — only how it gets set changes.

Simplest of all if a selector proves fiddly: ship separate discs per player
count. The build differences are small.

### Gate results (2026-08-05)

`spyro1x2/` builds with `make setup` then `make`.

| Check | Result |
| ----- | ------ |
| Rebuilt `SCUS_942.28` vs original | **byte-identical**, `84e3728a...` |
| Rebuilt full disc vs original ROM | 1,185 bytes differ of 661,547,040 (0.0002%) |

The disc difference is a single region spanning sectors 18-22. The first file
(`SYSTEM.CNF`) is at LBA 23, so **every byte of every file is identical** — the
difference is purely ISO 9660 metadata (volume descriptors, path tables,
directory records) written differently by mkpsxiso 2.30 than by Sony's 1998
mastering tool. Same benign class as stage 1.

**How to use this gate from now on.** Once hooks are added, `make` will fail by
design — that is expected. Switch to asking *"did ONLY the bytes I intended
change?"*:

```
cmp -l rom/SCUS_942.28 build/rom/SCUS_942.28 | wc -l
```

One replaced instruction = at most 4 differing bytes. If a one-instruction hook
reports hundreds of differing bytes, a `.incbin` length is wrong and everything
after it has shifted. Check this after EVERY new hook.

**WALK-IN-PLACE: SOLVED (2026-08-17).** Root cause was none of the state
suspects below — it was the buffered-input ring off-by-one (see CLAUDE.md):
P2's pad poll ran AFTER P1's poll had incremented `g_UnprocessedFrames`, so
P2's input landed one ring slot late and his first physics substep every frame read
stale input. Same root cause as his minimum-height jumps. The list below is
kept for reference only.

**Walk-in-place suspects, straight from the audit** (bug parked by the user;
start HERE when resuming, not with trial and error): around player 2's Spyro
tick, Spyromain swaps (a) the CAMERA — and our measurements show Spyro 1's
update writes `g_Camera` fields — and (b) per-player tick counters
(`sp2_ticks`/`sp2_tick_counter`) plus `sp2_calculation_results`. We swap none
of those during P2's tick. Also unswapped: the buffered-input ring index
(`g_UnprocessedFrames`) that Spyro's substep loop consumes via `g_ActivePad`.

**Flame renderer note:** spyro-1's `r_flame.s` = `func_80058D64` = the flame
draw; open-spyro misnames it `DrawSpyroHornStrikeTrails`. Guard byte
`0x80078760` (inside the flame block we swap). Third per-Spyro draw call,
after body and shadow — Spyromain's `Sp2RenderFlames` parallel.

## Port batches (2026-08-17) — his FILE boundaries are the batch size

All of Spyromain's code is now read. Lesson learned the hard way: porting HALF
of a coherent unit (LogicSpyro's swap list minus camera/ticks/calc-results)
produces partially-swapped-state bugs — the worst kind. Port whole files.

1. **Complete the P2 tick context** — the rest of `Sp2x2LogicSpyro`'s swap
   list around P2's tick: camera (`g_Camera`, `0x80076dd0` — spyro-1 models it
   as ONE struct; get its size from `include/camera.h`), tick-counter
   equivalents, calculation-results equivalent. THIS IS ALSO THE WALK-IN-PLACE
   SUSPECT BATCH.
2. **LogicCamera** — camera update per player = real camera follow for P2.
3. **Render sync loops** — moby `is_drawn` + particle sync between the two
   draw passes (RenderEntities tail + RenderParticles).
4. **UpdateMobys** — enemies interact with both Spyros (564 lines, biggest).
5. **Events** — LogicDialogue, StopCutscene, Sp2x280021610 (cutscene applied
   to BOTH cameras), TeleportSpyro (portals!), GetSoundVolumeFromDistance
   (sound = nearest player).

**LATENT BUG, found reading his hook list:** he hooks InitSpyroTwin at THREE
level-entry sites — P2 is re-seeded every level. Our lazy init's READY flag
(`0x8000ED00`) never resets, so on level change P2 keeps the OLD level's
position. Will bite the first time anyone exits Artisans Home. Fix belongs in
batch 1 (find Spyro 1's level-entry hook site, or reset READY when
`g_nCurrentLevelId` changes).
